# GMS Web Migration Plan

## Overview

Migrating the GMS (Godown Management System) from VB6 + SQL Server to Node.js + React + MySQL.
Multi-database architecture: one MySQL database per company, plus a central `gms_admin` database.

---

## VB6 Primary Key Format (SerialID System)

In the VB6 system, all primary keys are generated by `gudfGenSerialID()` in `CommFunc.bas`.
The function reads from a `SerialID` table (keyed by `pkSerialId`) and returns `LastID + 1`.

The `pkSerialId` values follow two formats:

### Shared / Common Masters (Group-level)
Used for State, Holiday, Item, Godown, Employee, VCComboData.
These masters are shared by all companies in the group.

```
Format:  GroupID!SerialNum
Example: BHW!1, BHW!2, BHW!3
         VLCO!1, VLCO!2
```

The `!` delimiter separates the Group ID from the running number.
All companies in the BHW group share the same item list, so the PKs are group-scoped.

### Company-Specific Masters (Company-level)
Used for Tax, Bank, Party, RateChart, PartyGodownLink, and all Transactions.

```
Format:  CompanyID!BranchID!SerialNum
Example: ADS!HO!1, ADS!HO!2
         TEST!HO!1
         VLCO!HO!1
```

The `!` delimiter separates CompanyID, BranchID (always 'HO' = Head Office), and the running number.

### Web System PK Strategy
The web version uses **UUID v4** (`randomUUID()`) for all primary keys instead of the VB6 serial format.
UUIDs are globally unique — no SerialID table needed, no risk of duplicates across databases.

When migrating data from VB6:
- The VB6 `pkXxxID` value (e.g. `BHW!1`) is kept in a separate `LegacyID` column (if needed for reference).
- A new UUID is generated for each row and becomes the new `pkXxxID`.
- Foreign key references (e.g. `fkItemID = 'BHW!1'`) must be remapped to the new UUID during migration.

## Sync Mechanism (syncToGroup.js)

When the Primary company writes a shared master:
1. The record is saved to the Primary's own DB (`req.db`).
2. `syncToGroup()` gets all sibling company IDs from `connectionManager`.
3. It runs `Model.upsert(record)` in parallel (`Promise.all`) on every sibling DB.
4. All operations complete before the API responds to the client.

This ensures all company databases stay in sync without manual intervention.

---

## Cross-Company Queries (groupQuery.js)

For Transaction and Report sections that show data group-wide:
- `groupUnionRaw()` builds a `UNION ALL` SQL across all company databases in the group.
- Example: `SELECT * FROM \`gms_ads\`.\`mParty\` UNION ALL SELECT * FROM \`gms_test\`.\`mParty\``
- MySQL handles this natively since all databases are on the same server.
- No extra network hops; performance is equivalent to a single-DB query with a WHERE clause.

## Server Startup Sequence (server.js)

```
1. Connect to gms_admin (adminDB.authenticate())
2. connectionManager.init(adminDB)
   - Reads all active companies from gms_admin.mCompany
   - For each company: creates Sequelize pool for dbName (e.g. gms_ads)
   - Stores Map<compID -> Sequelize> and Map<groupID -> [compID]>
3. app.listen(PORT) -- only after all company DBs are ready
```

If `gms_admin` is unreachable, the server exits with code 1 (process manager restarts it).

## Authentication Flow (JWT)

```
Login Request: { compID: 'ADS', userCode: 'ADMIN', password: '...' }
  1. Look up ADS in gms_admin.mCompany -> get fkGroupID='BHW', IsPrimary='Y', dbName='gms_ads'
  2. Look up user in gms_admin.mUser where fkGroupID='BHW' and UserCode='ADMIN'
  3. Verify bcrypt password
  4. Build JWT payload:
     { userId, compID:'ADS', groupID:'BHW', branchID:'HO', userCode, userFullName, roleID, isPrimary:true }
  5. Return: { token, user, permissions }

Every API request:
  - auth middleware verifies JWT, sets req.user
  - req.db = connectionManager.getDB('ADS')  -> gms_ads Sequelize instance
  - req.adminDB = adminDB                    -> gms_admin Sequelize instance
```

## Migration Steps (from gms_db to multi-DB)

### Step 1: Create gms_admin database
```sql
CREATE DATABASE gms_admin;
-- Copy from gms_db:
-- mCompanyGroup, mCompany (add dbName VARCHAR(50), IsPrimary CHAR(2) columns)
-- mUser, mRole, mPermission
```

### Step 2: Update mCompany with new columns
```sql
ALTER TABLE gms_admin.mCompany
  ADD COLUMN dbName VARCHAR(50) NOT NULL DEFAULT '',
  ADD COLUMN IsPrimary CHAR(2) NOT NULL DEFAULT 'N';

-- Set actual values:
UPDATE gms_admin.mCompany SET dbName='gms_ads',   IsPrimary='Y' WHERE pkCompID='ADS';
UPDATE gms_admin.mCompany SET dbName='gms_test',  IsPrimary='N' WHERE pkCompID='TEST';
UPDATE gms_admin.mCompany SET dbName='gms_vlco',  IsPrimary='Y' WHERE pkCompID='VLCO';
UPDATE gms_admin.mCompany SET dbName='gms_test1', IsPrimary='N' WHERE pkCompID='TEST1';
```

### Step 3: Create company databases
```sql
CREATE DATABASE gms_ads;
CREATE DATABASE gms_test;
CREATE DATABASE gms_vlco;
CREATE DATABASE gms_test1;
```

### Step 4: Create all tables in each company database
Run table CREATE scripts (from current gms_db schema) in each company database.
Tables needed in every company DB:
- Shared masters: mState, mHoliday, mItem, mGodown, mEmployee, VCComboData
- Company masters: mTax, mBank, mParty, mRateChart, mPartyGodownLink
- Transaction tables (future): mArrival, mDelivery, mBill etc.

### Step 5: Migrate shared master data (VB6 -> Web UUID format)
For each shared master table, data from gms_db goes to ALL company databases in the group.

Note on VB6 PKs: VB6 used `GroupID!SerialNum` format (e.g. `BHW!1`).
The web system uses UUID. During migration, generate new UUIDs for each row.
If any foreign keys reference the old PK format, they must be remapped.

```sql
-- Example for mItem (BHW group data goes to gms_ads AND gms_test):
INSERT INTO gms_ads.mItem SELECT * FROM gms_db.mItem WHERE fkGroupID='BHW';
INSERT INTO gms_test.mItem SELECT * FROM gms_db.mItem WHERE fkGroupID='BHW';
-- Repeat for mState, mHoliday, mGodown, mEmployee, VCComboData

-- VLCO group:
INSERT INTO gms_vlco.mItem SELECT * FROM gms_db.mItem WHERE fkGroupID='VLCO';
INSERT INTO gms_test1.mItem SELECT * FROM gms_db.mItem WHERE fkGroupID='VLCO';
```

### Step 6: Migrate company-specific data
Each company's data goes only to its own database.

```sql
-- mParty for ADS -> gms_ads only:
INSERT INTO gms_ads.mParty SELECT * FROM gms_db.mParty WHERE fkCompID='ADS';
INSERT INTO gms_test.mParty SELECT * FROM gms_db.mParty WHERE fkCompID='TEST';
INSERT INTO gms_vlco.mParty SELECT * FROM gms_db.mParty WHERE fkCompID='VLCO';
INSERT INTO gms_test1.mParty SELECT * FROM gms_db.mParty WHERE fkCompID='TEST1';
-- Repeat for mTax, mBank, mRateChart, mPartyGodownLink
```

### Step 7: Update .env file
```
ADMIN_DB_NAME=gms_admin
DB_HOST=localhost
DB_PORT=3306
DB_USER=root
DB_PASSWORD=yourpassword
# DB_NAME=gms_db  <-- remove this, no longer needed
```

### Step 8: Verify startup

## Phase 13 — Audit Report (frmAuditReport)

**Date:** 2026-08-01
**VB6 source:** `frmAuditReport.frm`, "Transaction Log" tab
**Module code:** `AUDIT_REP`

### Overview

Reads from VB6 audit trail tables (`AuditReport` configuration + `AuditReportColumns` column list +
the audit table itself). Dynamically builds the SELECT and WHERE clauses server-side.

Client-side post-processing mirrors `udfTLModifiedEntryCheck`:
- DEL rows highlighted #FFC0C0
- UPD2/UPD1 adjacent pairs: bold differing cells; remove both if identical

**VB6 bug fixed:** Original `Or` condition in `udfTLGenQury` always evaluated to True,
so the date WHERE clause was unconditionally appended even when no field was selected.
Fixed: WHERE clause only added when `dateField` is non-empty and validated.

### DB Tables Required (company DB)

| Table | Purpose |
|-------|---------|
| `AuditReport` | `(pkAudRepID, RepName, TableName, Active)` — one row per audit report |
| `AuditReportColumns` | `(cpkAudRepID, ColName, ColDisplayName, ComposeFlg, SortOrder)` — col definitions |

`SortOrder=1` must be `UniqueSrNo_AT`, `SortOrder=2` must be `Status_AT` — required for UPD1/UPD2 detection.
